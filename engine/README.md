# PortForge Engine

The PortForge Engine is PortForge's own build of the [ScarletNX](https://github.com/scarletnx/ScarletNX) runtime (GPL-3.0-or-later), changed to reduce some compilation stalls in games converted from the Switch. PortForge ships it in its `Engine` folder and installs it under a converted game from the **Engine** tab, keeping the original engine so it can be put back.

## What it changes

**Command stream guard** (Engine 1.16). A game waits for each submission's GPU fence with a timeout (one waits 100 ms per frame), which a console GPU never runs into. On a first run, when the driver's pipeline cache is cold, the GPU thread could fall several seconds behind. The game's wait then timed out, it took the work as finished and wrote its next frame's commands over GPU command memory the engine had not read yet. The engine then executed another frame's words as commands, the fences of every later frame stopped completing, and the game stayed at 3 to 5 FPS (210 and 310 ms frames, every thread idle). Entries after a SYNC entry are now also copied at submission. They are still read when the GPU thread reaches them, as before, and the submitted copy runs only when that memory changed after the game's own wait ioctl gave up on the submission's fence. Measured in one game's opening on a Ryzen 7 9800X3D and Radeon RX 9070 XT: before, 4 of 4 first runs with a cold cache and every run with pipeline creation slowed on purpose were corrupted. After, none of 7 (5 cold-cache runs, 2 slowed), and the game returns to its full frame rate after the loading freeze.

**Shader workers on Windows** (Engine 1.16). The automatic worker count read the CPUs the runtime pins threads to, which Windows doesn't report, so every Windows PC got two workers. The engine now counts the CPU threads and physical cores there: half of the physical cores from 6 cores on (at most 6), the earlier thread-based rule below that. An 8-core CPU gets 4, which shortened a cold-cache first run's total loading freezes from about 7.3 s to 5.9 s in one game.

**Game menu** (Engine 1.15). Esc opens the engine menu and goes back through its pages instead of quitting. Right-click does the same. Controllers use Home/Guide, or hold Back/Share/Minus and press Start/Options/Plus on the same physical pad, independently of game mappings. Ordinary Start/Back presses remain game input. Menu navigation supports keyboard, controller, touch and mouse; selecting Exit closes the game. Auto-repeat and held controller buttons/sticks cannot accidentally activate a freshly opened menu. The menu captures player input while open; the game simulation continues.

**Graphics protection** (`render_scale_safety=1`, default since Engine 1.9). The renderer's internal resolution path scales every intermediate render target, including images that later serve as game data. At 75% this reproduced severe world/geometry corruption in Mario. The default now keeps the actual internal scale at 1.0 at renderer startup, even with an older non-native `resolution` setting. It leaves guest target dimensions, fragment coordinates, texture queries/fetches and storage/writeback at their native relationship. Presentation upscaling is independent and remains enabled. This is a conservative compatibility path, not a completed implementation of arbitrary internal scaling. Advanced `render_scale_safety=0` retains the experimental old path; the app's normal save and matching controls enforce protection and show 100%.

**Speed lock** (`speed_lock`, on by default since Engine 1.5). A game that asks for a swap interval counts its frames, so presenting sooner than that interval ran the game itself faster, and later ran it in slow motion. With the lock on, `present_pace` always paces such a game at its interval, whatever the FPS limit (a number, 0 for none, or F4). Since Engine 1.6 a lower limit keeps some of the game's frames off the display (`present_show_due`, still drawn and submitted) instead of slowing the game. A game asking for interval 0 is paced only by a set limit. `speed_lock=0` restores the old behavior.

**Frame guard** (`frame_guard`, on by default since Engine 1.4). All skippable pipeline binds in a presented frame share one 1.5 ms optional wait budget. Earlier versions allowed 1.5 ms at every bind, which could add up during a burst of new pipelines. Time spent waiting for required pipelines also consumes the optional budget; required draws themselves still complete. The recording queue carries an ordered frame marker so the budget belongs to the frame being recorded, even if the GPU producer runs ahead. OS scheduling may overshoot a timed wait; subsequent optional waits then stop for that frame.

Cached background pipeline jobs can occupy at most one fewer than the available shader workers when there are two or more. Demand jobs can use every worker. Automatic worker counts are chosen on each launch: one on machines with four or fewer threads, then two to six, and half the physical cores from 6 cores on (Engine 1.16; before it, Windows PCs always got two). Explicit thread counts remain available. New conversions made by a frame-guard engine use automatic shader and JIT worker settings so copying the game does not pin those counts to its build PC.

FPS pacing drops the old scheduling deadline when the limit or native game interval changes. This prevents an obsolete future deadline from causing an avoidable pause after a mode change. The requested game speed and FPS limit are preserved.

The engine reports the 99th-percentile frame time and its equivalent 1% low for each 600-frame sample. PortForge's measured tuning compares that alongside average FPS, freezes and the worst frame; when two profiles are within 0.5 ms at p99, it favors the higher render scale. These are measurements of the scenes tested, not a guarantee for later gameplay.

The shader/pipeline cache is keyed by the translated-shader ABI, GPU and driver rather than the engine build number. Compatible engine updates therefore reuse cached shaders; translator or pipeline-key changes still invalidate them, as do GPU/driver changes. This avoids needlessly repeating first-use shader compilation after routine engine updates.

**AMD FSR 1** (`upscaler=1`, automatic by default since Engine 1.8) runs the official FP32 EASU spatial reconstruction and RCAS sharpening shaders on the final SDR game image when the output window is larger. Engine 1.9 preserves native internal rendering; FSR scales the final picture to the output size without changing the game's timing. The two scratch images are reused across frames, with GPU barriers and no CPU readback or queue-idle wait. Unsupported formats, downscaling, equal sizes, and allocation failures use the original linear path. `upscaler=0` selects linear scaling. FSR applies to presentation only; ordinary engine screenshots and headless Auto tune do not include its output or cost.


**Pixel smoothing** (`pixel_smoothing=1`, off by default) is edge antialiasing in the manner of FXAA's quality path, since Engine 1.12. It runs on the game's own image before FSR, where a jagged step is still one pixel: it finds each edge and its direction, follows it to both ends and blends across it by where the pixel sits on the step, plus a subpixel blend for one-pixel specks. FSR's RCAS then sharpens less, so the steps do not come back. Flat areas are copied unchanged. It cannot add detail the game did not render, and text softens a little. (Engine 1.11 had a weaker neighbour blend after FSR.)
Engine 1.10 reports actual dispatch and bypass transitions with source/output sizes and TV/handheld mode. Equal or smaller output sizes bypass FSR; maximize the window to enlarge the image. PortForge's protected Performance preset uses `docked=0` with `upscaler=1`, allowing the game to choose its own lighter handheld layout without scaling data-bearing intermediate images. A lower layout is game-dependent. FSR adds GPU work; a speed benefit must come from the reduced rendering workload and must be measured. The app compares handheld and TV rendering, retaining TV when handheld shows no measured benefit. Offscreen Auto tune excludes FSR/presentation cost.

This upscaler is FSR 1. It needs no motion vectors and works through the existing Vulkan renderer on supported AMD, NVIDIA and Intel devices. Only the current AMD PC has been tested physically. It cannot remove CPU-bound game loading or guarantee doubled FPS or fixed 1% lows. Full-color input is assumed: guest UI is upscaled with the scene, and HDR/unusual formats stay on the original path. The MIT-licensed AMD headers and upstream pin are in `src/nx/gpu/vk/fsr1/`; the runtime package includes their license.

**Engine 1.18 frame generation** (`frame_generation=1`, experimental, off by default) is a separate PortForge implementation, not AMD FSR 3. Three luminance pyramid levels guide GPU block matching, median motion filtering and a midpoint estimate from two copied SDR game images. Unchanged HUD pixels remain exact; uncertain matches fall back toward the current real pixel. Unsupported image formats and allocation failures retain real-frame presentation. No game targets, depth buffers, motion vectors or saves are modified. A presentation thread schedules the real image after the estimated midpoint; it rechecks the deadline after taking the Vulkan lock so a stale timer cannot flush a newer frame early. Menus bypass interpolation and resetting/resize clears history. It adds GPU work and latency, and can show artifacts; it cannot guarantee 2x output on every device or display. Only the RX 9070 XT has been tested. `fg_dump=PREFIX` writes periodic before/midpoint/after triplets for inspection (test use).

**Frame-time trace** (`frame_trace=1`, CSV beside the game log) records real game frames, timings and hitch attribution. `frametime_graph=1`, F7 or Escape toggles the graph. Generated output frames are excluded from game performance measurements. See `../VALIDATION-0.34.md` for actual tests and the save-state/native-resolution/FSR 3 limits.

**Smart async shaders** (`async_shaders`, on by default). The original engine stops the game whenever a draw needs a GPU pipeline that isn't built yet. The PortForge Engine waits at most 1.5 ms, then skips that draw for one frame, but only when every image the draw writes was drawn in each of the last three frames (the game's 3D world). Draws into anything else, such as menus, loading screens and images drawn once, still wait, so nothing goes missing for good.

Historical Engine 1.0 measurement on one game's opening with an empty shader cache (45 seconds of scripted play): 20 frames over 50 ms with the worst at 4,234 ms and 7,660 ms spent waiting became 4 frames over 50 ms (all loading) with the worst at 349 ms and 1 ms waiting. This is not a benchmark of Engine 1.3 or a prediction for other games. See [0.17 validation](../VALIDATION-0.17.md) for current evidence and limitations.

## Source and build

**Background shader translation** (`async_translation`, experimental, off by default). First-use shaders can be translated by the existing worker pool from copied code and constant buffers. The GPU thread validates recorded constant-buffer reads before reusing the finished shader. Snapshot jobs are bounded to 16 and completed jobs are collected once per submission, with synchronous fallback if the queue is full. Query-counting and transform-feedback draws wait. Graphics pipelines that write storage buffers or images also wait. Repeatedly drawn targets are a heuristic, not a guarantee that dropping a draw is harmless, so this option requires per-game testing.

This follows the general background-compilation approach documented by [DXVK](https://github.com/doitsujin/dxvk/wiki/Developer-guidelines) and explored by [dxvk-async](https://github.com/Sporif/dxvk-async). Their Direct3D DLLs are not compatible replacements for this engine's Vulkan renderer; no code or DLLs from those projects were copied. [Vulkan graphics pipeline libraries](https://docs.vulkan.org/features/latest/features/proposals/VK_EXT_graphics_pipeline_library.html) are a separate possible future change, not implemented in this release. A presentation filter cannot remove CPU loading work, and synthesizing pictures would not remove input latency.

- Base: ScarletNX commit `0de0a87` (the nightly of 2026-10-21).
- Changes: [`portforge-engine.patch`](portforge-engine.patch).
- Build on Windows: install MSYS2, run `msys-setup.sh` in it, then `build-engine.sh` and `package-engine.sh` (MSYS2 CLANG64 shell). The package lands in `engine/package`, which `build.ps1` copies into the app's `Engine` folder.
- Run the frame-policy, runtime-pacing and cache-file regression tests with `bash test-frame-guard.sh` in CLANG64 after configuring the engine. Tests and measurements for this release are documented in `VALIDATION-0.21.md` at the repository root.

## AI Engine Lab

With the engine source and MSYS2 on the PC, the Engine tab's **Let AI improve the engine** has Codex write a change for a game's recorded problems. PortForge builds it, measures it against the current engine on the same scripted play with an empty shader cache, and keeps it only when it reduces stutter by at least 20% without crashes or a lower frame rate. Anything else is reverted.
