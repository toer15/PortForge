# PortForge 0.60 / Engine 1.43 validation

Tested on Windows 11 with an AMD Radeon RX 9070 XT and a Ryzen 7 9800X3D on 2026-10-27, using copies of two converted games. The player's own folders and saves were not touched.

## Changes

- **AMD FSR 3 frame generation in the global settings.** The Upscaling choice is now "AMD FSR 3 frame generation". Generated pictures come from AMD FidelityFX SDK 1.1.4's published optical flow and frame interpolation (`amd_frame_generation`, on by default), and the global settings can set it for every game. Switch games give the PC no motion vectors or depth, so AMD's optical flow finds the motion and depth is flat. FSR 3's temporal upscaler needs those game motion vectors, so FSR 1 still does the upscaling.
- **A real FPS limiter.** Display FPS counts distinct pictures only: the game's frames, at most the limit, plus one AMD-generated picture between each two of them when the limit (and the monitor's refresh with VSync) leaves room for twice the game's frames. Engine 1.41 and 1.42 repeated held copies of real frames up to the limit and showed twice the limit with FSR 3. Those repeats are gone. The generated picture's half-frame wait now ends on Windows' high-resolution timer instead of a millisecond-rounded wait.
- **Crash guard, for every game.** `null_guard` is on by default. The game's lowest 64 KiB of memory, which nothing maps, becomes a zeroed scratch page. A game that uses a structure it failed to get (a null pointer) reads an empty one and keeps running instead of closing. The first touch of each page is logged as `crash guard: ...`. Set `null_guard=0` in a game's .ini to turn it off.

## Real-game results

- **Pokémon game.** Before this change, the game closed with an invalid memory access every time it opened the movie `d020_movie_a.bk2` (3 of 3 runs that reached it). With the crash guard on, the guard logged one null-pointer read at 154 s. The game then played the movie scene and reached gameplay, and the 260-second run ended normally. The final screenshot shows the game rendering correctly at 2560x1440. The cause of the null pointer is still open: the game's movie player computes an audio sample rate of 0, and the guard lets it continue past that.
- **Mario game, 60 seconds.** Settings: FPS limit 120, VSync on, 1440p true resolution, AMD FSR 3 frame generation. The display got exactly 120 pictures a second: 60 real and 60 AMD-generated (1,498 real and 1,500 generated by 26.5 s). True resolution held at 1.60x from the recorded 900 lines (2560x1440). Steady-scene p99 was about 17.2 to 17.6 ms with a 1% low of about 57 FPS, as in 0.59.

## Not established

- Whether the real limiter alone avoids the GPU resets seen in 0.59 with frame generation on. The Doctor's `safe_pacing` repair from 0.59 still applies.
- The crash guard keeps a game running after a null-pointer access, but it cannot make the game's behavior correct afterward. A game can still close for other reasons, such as a GPU device loss, a bad write elsewhere, or an unimplemented instruction.
