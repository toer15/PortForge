# Cloud save protocol

PortForge 0.19 supports OneDrive's Windows folder and HTTPS WebDAV. There is no hosted PortForge service. The per-game setting is off until the player configures a provider and enables it. Network work runs on a worker thread. UI timers change status text only when the result changes; form controls retain their theme during work.

Only `<stem>_data/save` is captured. SHA-256 covers sorted relative directory names and file contents. Capture is extracted and verified against the source hash before publication. Archives and restores have bounds of 256 MiB and 10,000 entries; traversal, reserved Windows names, duplicates and symlinks are rejected. A restore verifies the archive and tree hashes before swapping folders, keeps the previous local save beside the game, and rolls back the swap if installation fails.

Cloud objects are immutable `<guid>.zip` and `<guid>.json` pairs. Metadata contains version 1, revision ID, SHA-256 tree and archive hashes, UTC timestamp and parent revision IDs. Publication uploads the archive, downloads it to verify the checksum, then publishes metadata last. WebDAV uses `If-None-Match: *` and disables redirects. Metadata without a matching archive causes a retry instead of a restore. Authentication uses HTTPS Basic with the user's app password; passwords at rest use Windows DPAPI for the current user. Normal production configuration rejects HTTP.

Revisions form a graph. Its unreferenced nodes are current heads. Different head contents mean a conflict. A PC retains the last acknowledged revision and content hash to distinguish local changes, remote changes and simultaneous changes. No wall-clock timestamp decides which progress wins. Concurrent devices produce separate immutable heads. Explicit resolution creates a new revision parented to every known head. Previous revisions remain available in the provider folder. Missing local data on an established PC causes a conflict instead of publishing an accidental deletion.

The monitor synchronizes enabled games while the app is open and the game is stopped. A named mutex per executable serializes capture/restore and protected gameplay tests across app processes. Scripted tests register protection before modifying progress. An unfinished test backup also prevents automatic synchronization until recovery. Sync is checked before Play launches the game; launching an executable outside PortForge does not run that check.

OneDrive's read-back verifies the local sync folder only. PortForge cannot prove that the Windows client has uploaded it to the internet or that another device has hydrated every revision. It shows QUEUED and directs players to OneDrive's status. WebDAV verifies the actual server round trip. Offline and authentication errors preserve local progress. A player can stop future uploads by turning the switch off; OneDrive owns any already queued Windows transfers.

Tests use two independent local PC configurations and an authenticated loopback WebDAV server exercising MKCOL, PROPFIND, PUT and GET. HTTP is allowed only by an explicit test transport constructor and only for loopback addresses. Local tests do not establish interoperability with a live OneDrive or Nextcloud account. See VALIDATION-0.19.md for validation and remaining limits.
